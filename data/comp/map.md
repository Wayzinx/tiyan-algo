**默认原则：先用 MySQL，遇到具体瓶颈再加组件。** 每加一个组件之前先回答四个问题：它解决什么问题？带来什么新问题？怎么测？坏了怎么办？

| 组件 | 一句话定位 | 擅长 | 不擅长 | 什么时候上 |
|---|---|---|---|---|
| MySQL | 关系型数据库，数据的“真相” | 事务、约束、复杂查询、可靠持久化 | 超高并发热点读、全文搜索、海量数据分析 | 默认起点，大多数业务先用它 |
| Redis | 内存键值库 | 低延迟读写、计数、排行榜、锁、限流、TTL | 大容量、复杂查询、强一致 | 读多写少的热点；需要原子计数 / 锁 / 限流 |
| 本地缓存 | 进程内缓存 | 最快（没有网络开销） | 多实例之间不一致、容量小 | 数据小而稳定、允许短暂不一致；放在 Redis 前做一级缓存 |
| Kafka | 分布式日志型消息队列 | 超高吞吐、消息可回放、多组消费 | 原生延迟消息、复杂路由 | 埋点 / 日志 / 数据管道、事件流 |
| RocketMQ | 业务型消息队列 | 事务消息、延迟消息、顺序消息 | 生态偏 Java，流式分析不如 Kafka | 订单、支付等业务事件 |
| RabbitMQ | AMQP 消息代理 | 灵活路由、低延迟、逐条确认 | 超高吞吐、海量堆积 | 任务队列、需要复杂路由的中小规模场景 |
| Elasticsearch | 搜索与分析引擎 | 全文检索、多条件筛选、聚合 | 强一致、事务、频繁更新同一文档 | 搜索框、日志检索、复杂筛选列表 |
| MongoDB | 文档数据库 | 灵活 schema、嵌套文档 | 复杂 join 与跨文档事务 | 结构多变的数据：内容、配置、用户画像 |
| ClickHouse | 列式分析数据库 | 海量数据聚合查询快 | 高频单行更新、事务、点查 | 报表、埋点分析、监控指标 |
| Nginx / 网关 | 流量入口 | 反向代理、负载均衡、TLS、限流、路由 | 业务逻辑 | 所有对外服务的入口 |
| etcd / ZooKeeper | 强一致协调服务 | 配置中心、选主、服务发现、分布式锁 | 大数据量、高频写 | 需要强一致的少量元数据 |
| Docker / K8s | 容器与编排 | 环境一致、快速部署、弹性伸缩 | 有状态服务运维复杂、学习成本高 | 测试环境、微服务部署 |

**最常被问的三个选择**

- **要不要加 Redis？** 先确认瓶颈是 MySQL 的读，并且 SQL 和索引已经优化过；读多写少、热点集中、能容忍短暂旧数据才加。详见「Redis」的“什么时候不用”。
- **同步调用还是 MQ？** 下游慢、可以晚点完成、需要削峰或一个事件通知多方时用 MQ；需要马上拿到结果、强一致的步骤就同步调用。
- **MySQL 的 LIKE 还是 ES？** 数据量小、只做前缀匹配时 MySQL 就够了；要分词全文搜索、相关度排序、多条件组合筛选时才上 ES，并接受数据同步带来的延迟。

**面试里回答“说说你对 X 的理解”的顺序**：一句话定位 → 两三个核心特性 → 优点 → 缺点和代价 → 什么时候用、什么时候不用 → 我测它时关注什么。
